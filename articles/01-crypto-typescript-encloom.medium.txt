Buffer vs Uint8Array in TypeScript crypto (and why it hurts)

In Node, Buffer shows up almost by default. In the browser and on the edge, the real contract is typed arrays—Uint8Array—and often Web Crypto.

That split is easy to ignore until you ship the same crypto path across an API on Node, a client in the browser, and maybe a Worker in between. Then “call SHA-256” stops being the hard part. The hard part becomes converting types at every boundary, guessing whether a helper wants string | Buffer | Uint8Array, and dragging half a library into the bundle for one primitive.

This piece follows one idea end to end: treat bytes as Uint8Array, make encoding explicit, and keep imports small. The examples use encloom (https://www.npmjs.com/package/encloom). The same habits apply if you prefer @noble plus Web Crypto by hand.

This is not a threat-modeling or compliance guide. It is about bytes and APIs.


The contract: explicit bytes

A string is not a cryptographic message until you define an encoding. For JSON APIs, UTF-8 is the usual choice.

[Paste the following as a Medium code block — TypeScript]

import { sha256Sync, sha256Utf8HexSync } from "encloom/sha2";
import { utf8ToBuffer, bufferToHex } from "encloom/helpers/encoding";

const digest = sha256Sync(utf8ToBuffer("hello"));
console.log(bufferToHex(digest));

// Shortcut when you only need hex of a UTF-8 string
console.log(sha256Utf8HexSync("hello"));

[End code block]

Uint8Array in the public API avoids “sometimes Buffer, sometimes not” across runtimes. You pay one conversion line. You get predictable typing.

One naming trap: helpers like utf8ToBuffer still return Uint8Array. The Buffer suffix is an enc-utils-style name, not Node’s Buffer class.


Per-module imports

If your bundler tree-shakes and the package sets sideEffects: false, import the subpath you actually use.

[Paste as code block — TypeScript]

import { sha256Sync } from "encloom/sha2";
import { aesGcmEncryptSync } from "encloom/aes-gcm";

[End code block]

Same idea as preferring lodash/get over import _ from "lodash" when you need one function. On the frontend and in Workers, size shows up.


HMAC: integrity for a JSON body

Same byte contract: the MAC is computed over Uint8Array, not a loose string or a Node Buffer. Scenario: client and server share a secret and want to detect payload tampering. No encryption here—message authentication only.

[Paste as code block — TypeScript]

import {
  hmacSha256SignJsonUtf8KeyBase64Sync,
  hmacSha256VerifySync,
} from "encloom/hmac";
import { utf8ToBuffer, base64ToBuffer } from "encloom/helpers/encoding";

const secret = "api-shared-secret";
const body = { action: "ping", id: 1 };

const macB64 = hmacSha256SignJsonUtf8KeyBase64Sync(secret, body);

// Same serialization the helper used when signing
const msg = utf8ToBuffer(JSON.stringify(body));
const ok = hmacSha256VerifySync(
  utf8ToBuffer(secret),
  msg,
  base64ToBuffer(macB64)
);

console.log({ macB64, ok });

[End code block]

A detail that breaks verification in production: if one side signs the object and the other re-parses JSON from the wire and runs JSON.stringify again, key order can change. Agree on canonical bytes—or sign an already-stable string—between client and server.


AES-GCM: JSON in an envelope

Still the same thread: plaintext and key as Uint8Array; the helper only serializes the result to strings for transport. GCM gives confidentiality plus integrity (the tag). encryptJsonAes256GcmSync generates a random key and IV and returns an envelope with iv, key, and stream. Decryption returns unknown—narrow it at the call site.

[Paste as code block — TypeScript]

import {
  encryptJsonAes256GcmSync,
  decryptJsonAes256GcmSync,
} from "encloom/aes-gcm";

const wire = encryptJsonAes256GcmSync({ user: "ana", role: "admin" });
// wire: { iv, key, stream } — the key travels inside the envelope

const again = decryptJsonAes256GcmSync(wire) as {
  user: string;
  role: string;
};

console.log(again.user);

[End code block]

Important so the example is not misread: anyone who has the full wire can decrypt, because the key is in the object. That fits a local sealed blob, or a layer you later protect with another key, KMS, or ECIES. It is not “I encrypted with a shared secret and only send the ciphertext.”

If you manage the key yourself, the low-level API is aesGcmEncryptSync(nonce, key, plaintext). There the operational rule is simple: do not reuse the same (key, nonce) pair. Twelve-byte nonces are the usual size.


ECDSA (secp256k1): sign the digest

Explicit bytes again: UTF-8 to Uint8Array, then the digest, then the signature. Many tutorials sign raw plaintext. In this API, sign and verify expect the message hash (for example SHA-256). verify does not return a boolean: if the signature is invalid, it throws.

[Paste as code block — TypeScript]

import { generateKeyPair, sign, verify } from "encloom/ecdsa";
import { sha256Sync } from "encloom/sha2";
import { utf8ToBuffer } from "encloom/helpers/encoding";

const { privateKey, publicKey } = generateKeyPair();
const digest = sha256Sync(utf8ToBuffer("transfer:42"));

const sig = sign(privateKey, digest);
verify(publicKey, digest, sig); // ok; on failure → throw

[End code block]

For Ethereum-style pipelines, keccak256 lives in encloom/sha3. Keccak-256 is not the same as SHA3-256 (FIPS). Different domains—do not mix them up.


When this approach helps (and when it doesn’t)

It makes sense if you share the same byte-oriented code across Node, browser, and edge; if you use a few primitives and care what lands in the bundle; and if you prefer types that do not lie—Uint8Array instead of “stringly bytes.”

It adds little if you already live inside a stack that covers most of your case—a full wallet SDK, for example—and you do not care about size or buffer types.


Where to go next
